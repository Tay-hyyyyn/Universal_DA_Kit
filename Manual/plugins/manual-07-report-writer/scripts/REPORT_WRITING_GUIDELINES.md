# Manual 범용 보고서 작성 가이드라인

이 문서는 `Manual/plugins/manual-07-report-writer/scripts/write_reports.py`,
Manual 단계별 MD/PDF, 그리고 다른 agent가 Manual 워크플로우를 사용할 때 따라야 할
보고서 작성 계약을 정의한다.

목표는 짧은 로그형 보고서를 넘어서, 처음 보는 사람도 `문제 -> 데이터 -> 실험 -> 채택 이유 -> 남은 리스크`
를 한 번에 이해할 수 있는 독립형 결과 문서를 만드는 것이다.

## 1. 기본 원칙

- 모든 사용자-facing 문구는 한글로 작성한다.
- 보고서는 `무엇을 했다 -> 왜 했나 -> 무엇이 달라졌나 -> 그래서 무엇을 채택했나` 흐름을 가져야 한다.
- 표와 그래프는 반드시 해석 문장과 함께 배치한다.
- 점수는 항상 `데이터 범위`, `검증 방식`, `sample/full 여부`, `target 처리(raw/log1p)`, `지표(MAE/RMSE 등)`를 함께 적는다.
- 최종 보고서는 내부 run 이름이나 실험 별칭을 모르는 사람도 이해할 수 있는 구조를 기본으로 한다.
- 외부 제출 점수, 내부 OOF/CV, holdout 점수는 절대 같은 의미로 섞어 쓰지 않는다.
- 채택하지 않은 가설과 대안도 남겨서 다음 분석가가 반복 실수를 줄일 수 있게 한다.

## 2. 보고서 종류

Manual에서는 보고서를 아래 3종으로 구분한다.

| 종류 | 목적 | 핵심 독자 | 필수 성격 |
|---|---|---|---|
| 1차 기본 보고서 | 데이터 구조, 도메인 해석, 질문 수집 | 분석가, 사용자 | 질문 유도형 |
| 실험 비교 보고서 | 피처/모델/검증/후처리 비교 | 팀원, 다음 작업자 | 의사결정 추적형 |
| 최종 결과보고서 | 최종 모델과 결과를 독립 설명 | 사용자, 팀원, 미래의 나 | 완결형 |

## 3. 최종 결과보고서 표준 형식

최종 결과보고서는 아래 섹션을 기본 템플릿으로 사용한다. 대회형 프로젝트면 `제출 이력`,
일반 프로젝트면 `실험 이력`으로 이름만 바꾸고 나머지 구조는 유지한다.

### 3-1. 헤더

헤더에는 아래 정보를 반드시 넣는다.

- 문서 제목
- 작성일
- 최고 점수
- 최종 점수 또는 현재 대표 점수
- 최종 run 이름
- 최종 제출 파일 또는 대표 산출물 경로

외부 점수가 없는 프로젝트면 아래처럼 적는다.

- 최고 OOF/CV 점수
- 최고 holdout 점수
- 외부 제출 없음 또는 미확인

### 3-2. 프로젝트 개요

첫 페이지에서 아래를 즉시 보여준다.

- 문제 목표
- 타깃 변수
- 데이터 크기(train/test, 그룹 단위 등)
- 평가 지표
- 타깃 분포 특징(평균, 표준편차, 왜도, heavy-tail 여부)
- 업무/공정/비즈니스 맥락

### 3-3. 제출 이력 또는 실험 이력

대회형 데이터에서는 `제출 이력`을, 일반 프로젝트에서는 `실험 이력`을 표로 정리한다.

권장 컬럼:

- 차수 또는 실험명
- 파일명 또는 run 이름
- 점수
- 검증 방식
- 핵심 변경점
- 채택/비채택 이유

### 3-4. 모델 실험 전체 요약

모델군별로 나누어 정리한다. 예:

- Tree/Boosting 계열
- Linear/Explainable 계열
- Sequence/Deep Learning 계열
- Stacking/Blending 계열

표 기본 컬럼:

- 모델명
- CV/OOF 점수
- holdout 점수
- target 처리(raw/log1p 등)
- 핵심 특징
- 장점/약점

### 3-5. 피처 엔지니어링

이 섹션은 충분히 상세해야 한다. 반드시 아래를 포함한다.

- 총 피처 수
- 새로 만든 피처군 목록
- 피처군별 목적과 근거
- 핵심 피처 공식 또는 의사코드
- 도메인 해석
- 실제 성능 변화 또는 해석 가치

권장 표:

- 피처군
- 개수
- 대표 피처
- 생성 이유
- 기대 효과
- 실제 효과

핵심 피처는 가능하면 코드 블록 또는 수식 블록으로 보여준다.

### 3-6. 핵심 발견 및 교훈

이 섹션은 보고서의 핵심 가치다. 아래 주제를 우선 포함한다.

- 검증-실전 점수 갭의 원인
- 일반화 실패 구간(seen/unseen, late-phase, rare segment 등)
- raw vs log1p 해석
- 앙상블 다양성 해석
- 공학/도메인 피처의 실제 기여
- 실패한 가설에서 배운 점

가능하면 `원인`, `증거`, `영향 추정` 형식의 표를 사용한다.

### 3-7. 외부/벤치마크/팀 비교

비교 가능한 대상이 있다면 별도 섹션을 둔다.

권장 표:

- 비교 대상
- 상대 접근
- 우리 접근
- 우리가 더 나은 점
- 우리가 부족한 점
- 채택 여부

### 3-8. 미해결 과제

좋은 최종 보고서는 해결하지 못한 문제를 숨기지 않는다.

각 항목에는 아래를 함께 적는다.

- 현재 영향
- 왜 아직 못 풀었는지
- 다음에 풀 방법

### 3-9. 향후 시도 권장

단순 TODO가 아니라 우선순위가 보이게 적는다.

권장 표:

- 방향
- 구체적 방법
- 기대 효과
- 위험
- 우선순위

### 3-10. 주요 코드/아티팩트 파일

반드시 재현 경로를 남긴다.

필수 목록:

- 최종 학습 스크립트
- 피처 생성 스크립트
- 주요 리포트/메트릭 파일
- 제출 파일 또는 대표 예측 산출물
- tuning/weights/importance 파일

각 항목에는 `설명`, `용도`, `대표 점수`를 함께 적는다.

## 4. 1차 기본 보고서와 비교 보고서 형식

### 4-1. 1차 기본 보고서

아래는 필수다.

- 데이터 기반 시뮬레이션
- 데이터 개요
- 기본 상관계수/분포 시각화
- 제조업·공정 질문 또는 도메인 질문
- 기계공학/업무/사용자 배경 질문
- 초기 가설 -> EDA -> 피처 후보 연결

### 4-2. 실험 비교 보고서

아래 구조를 기본으로 한다.

- 비교 목적
- 비교 대상 실험 표
- 달라진 것(피처/모델/검증/후처리)
- 좋아진 점/나빠진 점
- 유지할 것/폐기할 것/보류할 것
- 다음 실험 우선순위

## 5. 단계별 작성 규칙

| 단계 | 필수 산출물 | 작성 기준 |
|---|---|---|
| 00 데이터 리뷰 | `dataset_review.md`, `column_dictionary.csv`, `data_overview.json` | 데이터 기반 시뮬레이션, 타깃, 컬럼군, 기초 통계, 도메인/공학 질문, 사용자 배경 질문을 남긴다. |
| 01 환경 점검 | `env_check.md`, `env_check.json` | 입력 파일, 패키지, 실행 가능 여부를 한국어로 정리한다. |
| 02 진단 | `diagnosis_report.md`, `missing_reason_hypotheses.csv`, `target_outlier_summary.json` | 결측/이상치 원인 가설, 처리 추천, log1p 후보 여부, 도메인 확인 질문을 남긴다. |
| 03 피처 생성 | `feature_build_report.md`, `feature_manifest.json`, `feature_candidate_menu.csv` | 피처군, 공식, 생성 이유, 누수/다중공선성 위험, 검증 계획을 남긴다. |
| 04 검증 분할 | `sample15_fold_report.md`, `sample15_fold_summary.json` | sample/full, group/time split, 누수 방지 근거를 남긴다. |
| 05 모델 학습 | `explainability_report.md`, `metrics.csv`, `tuning_results.csv` | 모델 선택 이유, 튜닝 범위, best params, train-valid gap, OOF/holdout 성능을 남긴다. |
| 06 제출 | `submission_report.md`, `postprocess_choices.json`, `ensemble_weights.csv` | 앙상블 방식, 후처리, raw/log 복원, sample 정렬 보존 여부를 남긴다. |
| 07 PDF 작성 | `stage_*.pdf`, `analysis_report_integrated.pdf` | 통합 PDF는 최종 결과보고서 표준 형식을 따르는 독립형 문서여야 한다. |

## 6. 시각화 배치 원칙

- 그래프는 반드시 `질문/가설` 바로 아래에 둔다.
- 그래프 뒤에는 1~3문장 해석을 붙인다.
- 최종 결과보고서에는 아래 시각화를 우선 포함한다.
  - 타깃 raw/log1p 분포
  - 실험/제출 이력 score 비교
  - 모델군별 성능 비교
  - feature importance
  - OOF correlation 또는 ensemble diversity
  - 일반화 성능 비교(holdout, rare segment, phase)
  - 제출 또는 예측 분포
- 본문에는 상위 8~15개만 넣고, 전체 CSV/JSON 경로를 함께 둔다.

## 7. 점수 표기 규칙

모든 점수는 아래 형식으로 기록한다.

- 지표명
- 값
- 데이터 범위
- 검증 방식
- target 처리
- 비고

예:

- `OOF MAE = 8.83 (full 250000 rows, 5-fold GroupKFold, log1p blend)`
- `holdout MAE = 8.42 (layout holdout)`

금지:

- 맥락 없이 `MAE 8.82`만 쓰는 것
- sample 점수를 full 점수처럼 적는 것
- 외부 점수와 내부 점수를 한 행에서 혼동하는 것

## 8. 피해야 할 빈약한 보고서 패턴

- 최종 점수와 파일 경로만 적은 상태
- 내부 실험명만 나열하고 내용 설명이 없는 상태
- 피처 이름만 적고 공식/의미/효과를 설명하지 않는 상태
- 앙상블을 했다고만 쓰고 구성/가중치/다양성 해석이 없는 상태
- 실패 실험과 버린 가설이 완전히 사라진 상태
- PDF와 MD에서 같은 모델을 다르게 설명하는 상태

## 9. README/Manifest 정합성

`Manual/README.md`, `Manual/agent_manifest.json`, `Manual/plugins/manual-07-report-writer/scripts/write_reports.py`
는 모두 아래 표현을 같은 의미로 사용해야 한다.

- 프로젝트 개요
- 제출 이력 또는 실험 이력
- 모델 실험 전체 요약
- 피처 엔지니어링
- 핵심 발견 및 교훈
- 미해결 과제
- 향후 시도 권장
- 주요 코드/아티팩트 파일

## 10. 검증 체크리스트

- 가이드가 `짧은 로그형`이 아니라 `독립형 결과 문서`를 요구하는지 확인한다.
- README와 manifest가 같은 구조를 참조하는지 확인한다.
- 최종 결과보고서 작성 시 필수 섹션이 빠지지 않는지 점검한다.
- 점수 표기가 sample/full/holdout/LB를 혼동하지 않는지 확인한다.
